# Памятка для защиты

**Что выполнено?** Три подтверждённые находки разных классов: SQL injection, reflected XSS и CRLF/header injection. Проверки не требовали входа. Основной отчёт содержит команды, реальные ответы и ограничения выводов.

**Почему SQL-инъекция подтверждена?** Истинное условие сохранило те же девять товаров, что и обычная категория Gin; ложное убрало все товары. Повтор дал тот же результат. Это управление логикой, а не просто HTTP-ошибка. Данные БД не выгружались.

**Почему не Critical?** Не доказаны масштаб доступа к БД, чтение секретов, запись и исполнение команд. High — оценка риска подтверждённой SQL-инъекции без авторизации.

**Почему XSS, а не просто отражение ввода?** Браузер действительно показал alert с маркером 20261106. Кавычка сама по себе экранировалась; комбинация с обратной косой чертой завершила JavaScript-строку. Сохранены ответ и текстовое наблюдение диалога.

**Помогает ли HttpOnly?** Он запрещает чтение соответствующей cookie из JavaScript. Он не устраняет выполнение кода в origin, подмену интерфейса или запросы с правами пользователя.

**Что именно доказано для CRLF?** Появление нового HTTP-заголовка X-Practice-Poc. Не доказаны cache poisoning, кража сессии или два отдельных HTTP-ответа. Это сознательное ограничение формулировки.

**Почему не использовали сканер?** Для выбранных проверок достаточно отдельных запросов и браузера. Уменьшены нагрузка и число неподтверждённых срабатываний.

**Почему нет числа CVSS?** Условия задания разрешают качественную оценку CIA и бизнес-рисков. Непроверенные последствия не подставлялись в метрики ради высокого балла.

**Какие два класса есть в работе?** Классы конкретных слабостей: SQL injection, XSS и HTTP header injection. Все три относятся к широкой группе технических уязвимостей, но механизмы и способы исправления различаются.

**Что сделать перед сдачей?** Прочитать отчёт, самостоятельно повторить три PoC в указанном scope, убедиться в доступности Merge Request для ревьювера. Не нажимать Merge, если работа должна оставаться на ревью.
