## 2. Краткое резюме

Подтверждены четыре находки из двух широких групп задания. Три технические уязвимости: SQL-инъекция, отражённая межсайтовая скриптовая атака (XSS) и внедрение HTTP-заголовка через символы перевода строки (CRLF). Все доступны без авторизации. SQL-инъекция позволяет управлять условием выборки товаров, XSS выполняет JavaScript при открытии специально сформированной ссылки, CRLF позволяет добавить произвольный HTTP-заголовок ответа. Четвёртая находка — конфигурационная: отсутствие заголовка HSTS в проверенных HTTPS-ответах, включая страницу входа. Она подтверждена обычными запросами без инъекций.

| Риск | Количество | Находки |
|---|---:|---|
| Критический (Critical) | 0 | Не подтверждены |
| Высокий (High) | 1 | F-01: SQL-инъекция |
| Средний (Medium) | 2 | F-02: отражённая XSS; F-03: внедрение HTTP-заголовка |
| Низкий (Low) | 1 | F-04: отсутствие HSTS в проверенных HTTPS-ответах |

**Соответствие широким группам из задания:**

| Находки | Широкая группа | Основание |
|---|---|---|
| F-01 SQL-инъекция, F-02 XSS, F-03 CRLF | Технические уязвимости | Обработка ввода позволяет менять SQL, JavaScript или структуру заголовков |
| F-04 Отсутствие HSTS | Конфигурационные ошибки | В обычных HTTPS-ответах не задана политика обязательного HTTPS; исправляется настройкой выдачи заголовка |

Таким образом, F-01 и F-04 относятся к разным широким группам. CRLF остаётся технической уязвимостью. Для F-04 подтверждён дефект конфигурации, а не успешный перехват трафика.

В первую очередь необходимо устранить SQL-инъекцию, затем XSS и CRLF; включение HSTS запланировать как отдельное усиление конфигурации. Уровни риска выбраны с учётом возможного ущерба и условий, необходимых для атаки. Числовой CVSS v4.0 не рассчитывался: задание допускает обоснование через конфиденциальность, целостность, доступность и последствия для продукта. Выгрузка БД, захват учётных записей и подмена данных в общем кэше не проверялись.

## 3. Методика и ограничения

1. Проверена доступность и прочитана страница разрешённых путей. Её перечень использовался для выбора гипотез, но не как доказательство уязвимостей.
2. Изучены HTML каталога `/catalog` и блога `/blog`, а также разрешённые для проверки сценарии JavaScript `/resources/js/searchLogger.js` и `/resources/js/deparam.js`.
3. Для SQL-инъекции сопоставлены исходный запрос и запросы с истинным и ложным условиями. Пара условий повторена для проверки воспроизводимости.
4. Для CRLF сопоставлены заголовки контрольного и изменённого запросов, внедрение повторено.
5. Для XSS проверено, как параметр вставляется в JavaScript. Выполнение кода подтверждено окном браузера с тестовым числом.
6. Для HSTS дважды получены заголовки обычных GET-ответов `/catalog`, `/login` и `/my-account` без cookie и без следования перенаправлениям. Отдельно прочитан публичный справочный статус preload; сканирование сторонних сервисов не выполнялось.
7. Ответы сохранены в `evidence/`; значения сессионных cookie и CSRF-токенов скрыты. Сохранённая cookie `category=Gin` является тестовым значением фильтра.

Burp Suite, ffuf, feroxbuster, Nuclei и Wapiti не запускались: выбранные гипотезы подтверждены отдельными запросами. Дополнительно выполнен обычный вход с опубликованной учебной парой `carlos / hunter2` и чтение `/my-account`: без входа получен 302 на `/login`, после ввода только имени — также 302, после пароля — 200; идентификатор сессии сменился. Эти наблюдения не оформлены как уязвимость. Другие роли, изменение заказов и профиля, XXE/SSRF, внешние интеграции и доступность под нагрузкой не проверялись. Пользовательские данные не изменялись. Для F-04 HTTP-трафик не перехватывался, запросы по незашифрованному HTTP не выполнялись. Обычная загрузка страницы браузером включает ресурсы интерфейса; частота 1 запрос/сек относится к последовательным проверочным HTTP-запросам, а не к загрузке всех ресурсов браузера.

## 4. Подтверждённые уязвимости

### 4.1. F-01 — SQL-инъекция в фильтре категории каталога

| Поле | Значение |
|---|---|
| Группа задания | Технические уязвимости |
| Класс | SQL-инъекция с проверкой истинного и ложного условий |
| Статус | Подтверждена (valid) |
| Риск / приоритет | Высокий (High) / P1 |
| Расположение | `GET /catalog`, параметр `category` |
| Модель атакующего | Неавторизованный посетитель; специальные права и действия жертвы не нужны |

**Описание и механизм.** Приложение выбирает товары по категории. При включении SQL-условия в `category` состав выдачи зависит от того, истинно условие или ложно. Это показывает, что пользовательский ввод влияет на логику запроса к базе данных. Исходный код сервера недоступен, поэтому точный текст SQL-запроса и тип СУБД не установлены.

**Метод обнаружения.** Сравнение ответов на обычный запрос и запросы с истинным и ложным условиями. Обычный запрос и истинное условие вернули одинаковые товары, ложное — пустую выборку. Так проверено влияние условия на результат.

**Шаги воспроизведения (PoC).** Выполнить последовательно, выдерживая паузу не менее секунды:

```bash
curl -sS --max-time 25 --get 'https://ginandjuice.shop/catalog' \
  --data-urlencode 'category=Gin'

curl -sS --max-time 25 --get 'https://ginandjuice.shop/catalog' \
  --data-urlencode "category=Gin' AND '1'='1'-- "

curl -sS --max-time 25 --get 'https://ginandjuice.shop/catalog' \
  --data-urlencode "category=Gin' AND '1'='2'-- "
```

Проверочный ввод:

```text
Gin' AND '1'='1'-- 
Gin' AND '1'='2'-- 
```

Сопоставить ссылки `/catalog/product?productId=...` в ответах, затем повторить запросы с истинным и ложным условиями.

**Ожидаемое поведение.** Неизвестная категория отклоняется либо трактуется как обычное строковое значение; SQL-фрагменты не управляют выборкой.

**Фактическое поведение и доказательства.** Все ответы имеют статус 200:

| Запрос | Идентификаторы товаров | Число |
|---|---|---:|
| Контроль `Gin` | 1, 6, 10, 13, 14, 15, 16, 17, 18 | 9 |
| Истинное условие | 1, 6, 10, 13, 14, 15, 16, 17, 18 | 9 |
| Ложное условие | нет | 0 |
| Повтор истинного условия | тот же набор | 9 |
| Повтор ложного условия | нет | 0 |

Сохранённые ответы: [контроль](evidence/sqli-control.txt), [истинное условие](evidence/sqli-true.txt), [ложное условие](evidence/sqli-false.txt), [повтор истинного условия](evidence/sqli-true-repeat.txt), [повтор ложного условия](evidence/sqli-false-repeat.txt).

**Влияние и риск.** Подтверждено изменение условия выборки товаров. В рабочем приложении такая ошибка может привести к раскрытию данных. Объём доступных данных зависит от запроса и прав учётной записи приложения в БД. Изменение/удаление данных и нарушение доступности не проверялись. Высокий риск выбран потому, что неавторизованный посетитель может влиять на SQL-запрос, а приложение может иметь доступ к другим данным. Чтение секретных данных не проверялось.

**Рекомендации.** Использовать параметризованные запросы: передавать `category` отдельно от текста SQL-команды. Дополнительно проверять категорию по списку допустимых значений, ограничить права учётной записи БД. Проверить остальные фильтры и поиск. Добавить тест, который проверяет, что оба приведённых значения обрабатываются как данные и не меняют логику SQL-запроса.

Руководство: [OWASP — предотвращение SQL-инъекций](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).

### 4.2. F-02 — Отражённая XSS в поиске каталога

| Поле | Значение |
|---|---|
| Группа задания | Технические уязвимости |
| Класс | Отражённая XSS, выход из строки JavaScript |
| Статус | Подтверждена (valid) |
| Риск / приоритет | Средний (Medium) / P2 |
| Расположение | `GET /catalog`, параметр `searchTerm` |
| Модель атакующего | Неавторизованный автор ссылки; жертва должна открыть ссылку |

**Описание и механизм.** Значение поиска вставляется в строку встроенного JavaScript, который заполняет поле поиска. Одинарная кавычка экранируется, но обратная косая черта обрабатывается недостаточно корректно. Комбинация `\'` позволяет завершить строку и выполнить последующий код. HTML-экранирование само по себе не обеспечивает безопасность JavaScript-контекста.

**Метод обнаружения.** Анализ строки `var searchText` в HTTP-ответе, проверка кавычки и обратной косой черты, затем открытие проверочной ссылки в браузере. Выполнение `alert` подтвердило, что ввод стал исполняемым кодом.

**Шаги воспроизведения (PoC).**

1. Открыть браузер; вход в учётную запись не требуется.
2. Перейти по адресу:

```text
https://ginandjuice.shop/catalog?searchTerm=%5C%27%3Balert(20261106)%3B%2F%2F
```

3. Убедиться, что появляется диалог от `ginandjuice.shop` с текстом `20261106`.
4. Закрыть диалог кнопкой OK. Никакие данные не отправляются на внешние адреса.

Проверочный ввод после декодирования URL:

```javascript
\';alert(20261106);//
```

Проверка отражения через HTTP:

```bash
curl -sS --max-time 25 \
  'https://ginandjuice.shop/catalog?searchTerm=%5C%27%3Balert(20261106)%3B%2F%2F'
```

**Ожидаемое поведение.** Ввод остаётся данными поля поиска, новый JavaScript не исполняется.

**Фактическое поведение.** Ответ содержит:

```javascript
var searchText = '\\';alert(20261106);//';
```

Две обратные косые черты интерпретируются как экранированная обратная косая черта; следующая кавычка закрывает строку. `//` комментирует остаток строки. Браузер показал диалог `alert` с маркером.

**Доказательства.** [HTTP-ответ](evidence/xss-confirmed.txt), [текстовое наблюдение браузера](evidence/xss-browser-observation.txt). На [снимке](evidence/xss-browser.jpg) видна страница, но окно сообщения в изображение не попало. Его появление зафиксировано в текстовом представлении интерфейса браузера; средство проверки также определило тип окна как `alert`.

**Влияние и риск.** Подтверждено исполнение JavaScript в контексте домена. Для реального продукта возможны подмена интерфейса, чтение данных, доступных коду страницы и действия с правами активной сессии жертвы. Cookie с HttpOnly нельзя напрямую прочитать через JavaScript; это не исключает других последствий XSS. Кража cookie, данных и действия в чужой сессии не выполнялись. Конфиденциальность и целостность потенциально затронуты; влияние на доступность не проверялось. Средний риск выбран с учётом того, что пользователь должен открыть ссылку. Действия с его данными или учётной записью не проверялись.

**Рекомендации.** Исключить прямую подстановку пользовательского ввода в исполняемый код страницы. Передавать данные отдельно и присваивать их полю через свойство `value`, а обычному тексту страницы — через `textContent`. Если вставка в JavaScript-строку необходима, использовать проверенную библиотеку кодирования для этого контекста, включая обработку обратных косых черт и границ HTML-тега. Политику безопасности содержимого (CSP) применять как дополнительную защиту. Проверить аналогичные вставки в поиске, сообщениях об ошибках и формах входа. Добавить браузерные тесты с кавычками, обратными косыми чертами и закрывающими тегами: ввод не должен исполняться как код.

Руководство: [OWASP — предотвращение XSS](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html).

### 4.3. F-03 — Внедрение HTTP-заголовка через `category` (CRLF)

| Поле | Значение |
|---|---|
| Группа задания | Технические уязвимости |
| Класс | Внедрение HTTP-заголовка через символы CR и LF |
| Статус | Подтверждена (valid) |
| Риск / приоритет | Средний (Medium) / P3 |
| Расположение | `GET /catalog`, параметр `category`, заголовок `Set-Cookie` |
| Модель атакующего | Неавторизованный посетитель; для воздействия на другого пользователя потребуется убедить его открыть ссылку или сочетать ошибку с другой уязвимостью |

**Описание и механизм.** Приложение записывает выбранную категорию в cookie. В значении `category` принимаются URL-кодированные CR и LF. После декодирования они разрывают строку заголовка, и следующий фрагмент воспринимается как самостоятельный HTTP-заголовок ответа.

**Метод обнаружения.** Сравнение заголовков контрольного запроса и запроса с безопасным маркером `X-Practice-Poc`. Проверялось наличие поля в заголовках, а не просто текста в HTML. Подтверждение повторено.

**Шаги воспроизведения (PoC).** Сначала выполнить контроль:

```bash
curl -sS --max-time 25 -D - -o /dev/null \
  'https://ginandjuice.shop/catalog?category=Gin'
```

Затем через секунду выполнить:

```bash
curl -sS --max-time 25 -D - -o /dev/null \
  'https://ginandjuice.shop/catalog?category=Gin%0D%0AX-Practice-Poc%3A%20GJ-20261106'
```

Проверочный ввод в наглядной записи (`\r\n` обозначает реальные CR/LF):

```text
Gin\r\nX-Practice-Poc: GJ-20261106
```

**Ожидаемое поведение.** Значения с управляющими символами отклоняются до формирования cookie; отдельный пользовательский заголовок не появляется.

**Фактическое поведение и доказательства.** В исходном ответе маркера нет, в изменённом и повторном есть:

```http
Set-Cookie: category=Gin
X-Practice-Poc: GJ-20261106; Secure; HttpOnly
```

Суффикс `Secure; HttpOnly`, предназначенный для cookie, попал в значение внедрённого заголовка. Ответ имеет статус 200. [Контроль](evidence/header-control.txt), [первое подтверждение](evidence/header.txt), [повтор](evidence/header-repeat.txt).

**Влияние и риск.** Подтверждён контроль над дополнительным полем HTTP-ответа, то есть нарушение его целостности. Возможность подмены cookie, перенаправления пользователя или изменения кэшированных данных зависит от того, как браузер и промежуточные узлы обрабатывают заголовки. Эти последствия, а также разделение ответа на два HTTP-сообщения не проверялись. Риск оценён как средний: структура ответа изменяется, но ущерб для других пользователей не установлен. Влияние на доступность не установлено.

**Рекомендации.** Проверять `category` по списку категорий и отклонять CR, LF и другие управляющие символы после декодирования. Для cookie и заголовков использовать штатные функции библиотеки, проверяющие значения. Не собирать заголовки из непроверенных строк. Проверить все пользовательские значения в `Location`, `Set-Cookie` и служебных заголовках. Добавить интеграционный тест: `%0D%0A` не создаёт нового поля ответа; категория с недопустимыми символами отклоняется.

Руководства: [OWASP — проверка входных данных](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html); механизм описан в [OWASP — разделение HTTP-ответа](https://community.owasp.org/attacks/HTTP_Response_Splitting). Второй источник описывает в том числе разделение на два ответа; в этой работе подтверждено только добавление заголовка.

### 4.4. F-04 — Отсутствие HSTS в HTTPS-ответах каталога и входа

| Поле | Значение |
|---|---|
| Группа задания | Конфигурационные ошибки |
| Класс | Не задана политика HTTP Strict Transport Security (HSTS) |
| Статус | Подтверждена (valid): отсутствие заголовка в проверенных ответах |
| Риск / приоритет | Низкий (Low) / P3 |
| Расположение | `GET /catalog`, `GET /login`, `GET /my-account` без авторизации |
| Модель атакующего | Активный посредник в сети; требуется попытка HTTP-навигации браузером без действующей HSTS-политики и без защиты, запрещающей переход на HTTP |

**Описание и механизм.** Сервер отвечает по HTTPS, но не передаёт `Strict-Transport-Security`. Поэтому эти ответы не устанавливают в браузере правило обязательного использования HTTPS для домена. Это самостоятельный дефект конфигурации транспортной защиты. Он воспроизводится без параметра `category`, CR/LF и других специальных данных и не зависит от F-03. TLS-подключение, которое уже установлено корректно, этим наблюдением не скомпрометировано.

**Метод обнаружения.** Прямое чтение всех заголовков обычных GET-ответов без входа, два прохода по трём разрешённым путям. Использованы GET, а не только HEAD, поскольку обработка этих методов может различаться. Перенаправление `/my-account` не выполнялось. Отсутствие проверялось без учёта регистра имени заголовка. Публичный справочник `hstspreload.org` вернул `status: unknown` и пустой `preloadedDomain`: он не сообщает о действующей preload-записи для домена. Этот справочный результат не доказывает состояние каждого браузера и не является отдельной уязвимостью.

**Шаги воспроизведения (PoC).**

1. Без cookie и авторизации запросить заголовки страницы входа:

```bash
curl -sS --max-time 25 -D - -o /dev/null 'https://ginandjuice.shop/login'
```

2. С паузой не менее секунды выполнить такие же GET-запросы к `/catalog` и `/my-account`. Не добавлять `-L`, чтобы сохранить исходный ответ 302.
3. Убедиться, что среди всех заголовков отсутствует `Strict-Transport-Security`; повторить три запроса.
4. Для автоматического повторения из корня репозитория выполнить:

```bash
python3 reports/gin-juice/scripts/check_hsts.py --output /tmp/gin-juice-hsts-recheck
```

Скрипт ограничен тремя указанными HTTPS-путями, делает шесть последовательных запросов с паузами, скрывает cookie и сохраняет только заголовки. При неожиданном статусе или появлении HSTS завершается ошибкой и не подтверждает отсутствие. Специальный payload не требуется: проверочный ввод — обычный GET без параметров и внедряемых заголовков. Перед публикацией ручного вывода curl необходимо скрыть значения `Set-Cookie`.

**Ожидаемое поведение.** HTTPS-ответы, включая перенаправления, передают действующую политику HSTS с положительным `max-age`.

**Фактическое поведение и доказательства.** Во всех шести ответах заголовок отсутствует:

| Путь | Первый / повторный статус | HSTS в обоих ответах |
|---|---|---|
| `/catalog` | 200 / 200 | Отсутствует |
| `/login` | 200 / 200 | Отсутствует |
| `/my-account` | 302 / 302, `Location: /login` | Отсутствует |

[Сводка](evidence/hsts-summary.txt); полные заголовки: [каталог 1](evidence/hsts-catalog-1.txt), [каталог 2](evidence/hsts-catalog-2.txt), [вход 1](evidence/hsts-login-1.txt), [вход 2](evidence/hsts-login-2.txt), [аккаунт 1](evidence/hsts-account-1.txt), [аккаунт 2](evidence/hsts-account-2.txt). [Справочный ответ preload](evidence/hsts-preload-status.txt). Время получения записано в UTC внутри файлов; локальная дата проверки — 6 ноября 2026 года.

**Влияние и риск.** У браузера без ранее сохранённой политики нет установленного этими ответами HSTS-запрета на HTTP. При HTTP-навигации активный сетевой посредник потенциально может подменять незашифрованный ответ или перенаправление. Возможны нарушения конфиденциальности и целостности; доступность не исследовалась. Современный HTTPS-only режим и ранее сохранённая политика могут предотвращать такой сценарий. Наличие `Secure` у сессионной cookie сохранено и не позволяет утверждать, что она отправляется по HTTP. Перехват пароля, понижение HTTPS до HTTP, доступность HTTP-сервиса и поведение конкретного браузера не проверялись. Риск низкий: подтверждён недостаток защиты, но успешная атака и ущерб не показаны. Отсутствие preload само по себе не считается ошибкой.

**Рекомендации и критерий закрытия.** Настроить выдачу HSTS на уровне приложения или завершающего TLS прокси во всех HTTPS-ответах, включая 3xx и ошибки. Начать с небольшого `max-age`, проверить совместимость и постепенно увеличить срок. Пример целевой политики для основного домена после проверки:

```http
Strict-Transport-Security: max-age=31536000
```

`includeSubDomains` добавлять только после проверки HTTPS на всех поддоменах; обязательное включение в preload не требуется. Добавить проверку заголовка в тесты конфигурации. Для закрытия повторить те же запросы и подтвердить корректную политику с положительным сроком во всех ответах; отдельно проверить её применение браузером в разрешённой тестовой среде.

Руководства: [OWASP HSTS Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Strict_Transport_Security_Cheat_Sheet.html), [рекомендации сервиса HSTS preload по развёртыванию](https://hstspreload.org/#deployment-recommendations).

## 6. Приоритеты исправления

| Приоритет | Находка | Причина | Критерий закрытия |
|---|---|---|---|
| P1 | F-01 SQL-инъекция | Управление серверной выборкой без входа, потенциальный риск БД | Параметризация внедрена; истинное и ложное условия не интерпретируются как SQL |
| P2 | F-02 XSS | При открытии ссылки выполняется JavaScript с правами страницы сайта | Проверочный ввод остаётся данными; код не выполняется |
| P3 | F-03 CRLF | Подтверждена подмена структуры заголовков; последующие атаки не проверялись | Управляющие символы отклоняются, дополнительного заголовка нет |
| P3 | F-04 HSTS | Отсутствует политика обязательного HTTPS, атака не демонстрировалась | Во всех проверенных HTTPS-ответах корректный HSTS с положительным `max-age` |

Приоритет определяет порядок исправления ошибок. F-02 и F-03 могут исправляться параллельно.

## 7. Итоговые рекомендации

1. Использовать параметризованные запросы во всех обращениях к БД. Выдать учётной записи приложения только необходимые права.
2. Не вставлять пользовательский ввод в исполняемый JavaScript. Для вывода текста использовать свойства страницы, которые не интерпретируют его как код.
3. Проверять значения cookie и HTTP-заголовков после декодирования. Отклонять управляющие символы. Настроить HSTS и проверять его выдачу в обычных HTTPS-ответах.
4. Добавить тесты для трёх описанных способов атаки и проверку HSTS, чтобы ошибки не появились снова. Запускать динамическое тестирование безопасности (DAST) в тестовой среде с заданными границами проверки и ограничением нагрузки.
5. Составить список входных параметров и мест, где они используются в SQL, JavaScript и HTTP-заголовках. Назначить ответственных за исправления и повторить проверку после изменений.
