## 2. Краткое резюме

Подтверждены три уязвимости трёх технических классов: SQL injection, reflected XSS и HTTP response header injection (CRLF). Все доступны без авторизации. SQL-инъекция позволяет управлять условием выборки товаров, XSS выполняет JavaScript при открытии специально сформированной ссылки, CRLF позволяет добавить произвольный HTTP-заголовок ответа.

| Риск | Количество | Находки |
|---|---:|---|
| Critical | 0 | Не подтверждены |
| High | 1 | F-01: SQL-инъекция |
| Medium | 2 | F-02: reflected XSS; F-03: внедрение HTTP-заголовка |
| Low | 0 | Отдельные находки не оформлялись |

В первую очередь необходимо устранить SQL-инъекцию, затем XSS и CRLF. Уровни — экспертная оценка влияния и условий эксплуатации. Числовой CVSS v4.0 не рассчитывался: задание допускает обоснование через конфиденциальность, целостность, доступность и бизнес-риски. Выгрузка БД, захват аккаунтов и отравление общего кэша не выполнялись и не заявляются как подтверждённые результаты.

## 3. Методика и ограничения

1. Проверена доступность и прочитана страница разрешённых путей. Её перечень использовался для выбора гипотез, но не как доказательство уязвимостей.
2. Изучены HTML каталога `/catalog` и блога `/blog`, а также перечисленные в scope скрипты `/resources/js/searchLogger.js` и `/resources/js/deparam.js`.
3. Для SQL-инъекции сопоставлены исходный запрос и запросы с истинным и ложным условиями. Пара условий повторена для проверки воспроизводимости.
4. Для CRLF сопоставлены заголовки контрольного и изменённого запросов, внедрение повторено.
5. Для XSS изучён контекст отражения параметра в JavaScript, затем выполнение подтверждено браузерным диалогом с числовым маркером.
6. Ответы сохранены в `evidence/`; значения сессионных cookie и CSRF-токенов скрыты. Сохранённая cookie `category=Gin` является тестовым значением фильтра.

Burp Suite, ffuf, feroxbuster, Nuclei и Wapiti не запускались: выбранные гипотезы подтверждены отдельными запросами. Нет результатов автоматического сканера, которые выдавались бы за ручную проверку. Роли авторизованных пользователей, операции заказа и профиля, XXE/SSRF, внешние интеграции, доступность под нагрузкой не проверялись. Вход и изменение пользовательских данных не выполнялись. Обычная загрузка страницы браузером включает ресурсы интерфейса; частота 1 запрос/сек относится к последовательным HTTP-пробам, а не к загрузке всех ресурсов браузера.

## 4. Подтверждённые уязвимости

### 4.1. F-01 — SQL-инъекция в фильтре категории каталога

| Поле | Значение |
|---|---|
| Класс | SQL injection, boolean-based |
| Статус | valid |
| Риск / приоритет | High / P1 |
| Расположение | `GET /catalog`, параметр `category` |
| Модель атакующего | Неавторизованный посетитель; специальные права и действия жертвы не нужны |

**Описание и механизм.** Приложение выбирает товары по категории. При включении SQL-условия в `category` выдача изменяется в соответствии с истинностью условия. Это свидетельствует о попадании пользовательского значения в синтаксис запроса к БД. Исходный код сервера недоступен, поэтому конкретная конструкция SQL и тип СУБД не утверждаются.

**Метод обнаружения.** Ручной дифференциальный анализ ответов. Контроль и истинное условие должны возвращать одинаковые идентификаторы, ложное — пустую выборку. Это сильнее единичной ошибки HTTP 500: сравнивается управляемое поведение успешных ответов.

**PoC.** Выполнить последовательно, выдерживая паузу не менее секунды:

```bash
curl -sS --max-time 25 --get 'https://ginandjuice.shop/catalog' \
  --data-urlencode 'category=Gin'

curl -sS --max-time 25 --get 'https://ginandjuice.shop/catalog' \
  --data-urlencode "category=Gin' AND '1'='1'-- "

curl -sS --max-time 25 --get 'https://ginandjuice.shop/catalog' \
  --data-urlencode "category=Gin' AND '1'='2'-- "
```

Payload:

```text
Gin' AND '1'='1'-- 
Gin' AND '1'='2'-- 
```

Сопоставить ссылки `/catalog/product?productId=...` в ответах, затем повторить пару true/false.

**Ожидаемое поведение.** Неизвестная категория отклоняется либо трактуется как обычное строковое значение; SQL-фрагменты не управляют выборкой.

**Фактическое поведение и доказательства.** Все ответы имеют статус 200:

| Запрос | Идентификаторы товаров | Число |
|---|---|---:|
| Контроль `Gin` | 1, 6, 10, 13, 14, 15, 16, 17, 18 | 9 |
| Условие true | 1, 6, 10, 13, 14, 15, 16, 17, 18 | 9 |
| Условие false | нет | 0 |
| Повтор true | тот же набор | 9 |
| Повтор false | нет | 0 |

Артефакты: [контроль](evidence/sqli-control.txt), [true](evidence/sqli-true.txt), [false](evidence/sqli-false.txt), [повтор true](evidence/sqli-true-repeat.txt), [повтор false](evidence/sqli-false-repeat.txt).

**Влияние и риск.** Доказано влияние на условие чтения товаров. Для реального продукта такой дефект создаёт высокий риск конфиденциальности БД; потенциальный масштаб зависит от запроса и прав учётной записи БД. Изменение/удаление данных и нарушение доступности не проверялись. High выбран из-за подтверждённого управления SQL без авторизации и потенциально широкого доступа приложения к данным, а не на основании доказанной выгрузки секретов.

**Рекомендации.** Перейти на параметризованные запросы с bind-параметрами; не склеивать SQL со строкой `category`. Дополнительно проверять категорию по списку допустимых значений, ограничить права учётной записи БД. Проверить остальные фильтры и поиск. Регрессионный тест должен доказывать, что оба payload обрабатываются как данные и не меняют SQL-логику.

Практика: [OWASP SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).

### 4.2. F-02 — Reflected XSS в поиске каталога

| Поле | Значение |
|---|---|
| Класс | Reflected XSS, выход из JavaScript-строки |
| Статус | valid |
| Риск / приоритет | Medium / P2 |
| Расположение | `GET /catalog`, параметр `searchTerm` |
| Модель атакующего | Неавторизованный автор ссылки; жертва должна открыть ссылку |

**Описание и механизм.** Значение поиска вставляется в строку встроенного JavaScript, который заполняет поле поиска. Одинарная кавычка экранируется, но обратная косая черта обрабатывается недостаточно корректно. Комбинация `\'` позволяет завершить строку и выполнить последующий код. HTML-экранирование само по себе не обеспечивает безопасность JavaScript-контекста.

**Метод обнаружения.** Анализ строки `var searchText` в HTTP-ответе, проверка кавычки и обратной косой черты, затем открытие PoC в браузере. Само отражение текста не считалось подтверждением XSS: подтверждено именно выполнение `alert`.

**PoC.**

1. Открыть браузер; вход в аккаунт не требуется.
2. Перейти по адресу:

```text
https://ginandjuice.shop/catalog?searchTerm=%5C%27%3Balert(20261106)%3B%2F%2F
```

3. Убедиться, что появляется диалог от `ginandjuice.shop` с текстом `20261106`.
4. Закрыть диалог кнопкой OK. Никакие данные не отправляются на внешние адреса.

Payload после URL-декодирования:

```javascript
\';alert(20261106);//
```

Проверка отражения через HTTP:

```bash
curl -sS --max-time 25 \
  'https://ginandjuice.shop/catalog?searchTerm=%5C%27%3Balert(20261106)%3B%2F%2F'
```

**Ожидаемое поведение.** Ввод остаётся данными поля поиска, новый JavaScript не исполняется.

**Фактическое поведение.** Ответ содержит:

```javascript
var searchText = '\\';alert(20261106);//';
```

Две обратные косые черты интерпретируются как экранированная обратная косая черта; следующая кавычка закрывает строку. `//` комментирует остаток строки. Браузер показал диалог `alert` с маркером.

**Доказательства.** [HTTP-ответ](evidence/xss-confirmed.txt), [текстовое наблюдение браузера](evidence/xss-browser-observation.txt). [Снимок страницы](evidence/xss-browser.jpg) является дополнительным контекстом: сам системный диалог в JPEG не попал; факт его появления зафиксирован в текстовом дереве интерфейса и типе `getJsDialog(): alert`.

**Влияние и риск.** Подтверждено исполнение JavaScript в контексте домена. Для реального продукта возможны подмена интерфейса, чтение доступных скрипту данных и действия с правами активной сессии жертвы. Cookie с HttpOnly нельзя напрямую прочитать через JavaScript; это не исключает других последствий XSS. Кража cookie, данных и действия в чужой сессии не выполнялись. Конфиденциальность и целостность потенциально затронуты; влияние на доступность не проверялось. Medium выбран с учётом необходимости открытия ссылки жертвой и ограниченного доказанного воздействия.

**Рекомендации.** Убрать подстановку ввода в исполняемый inline-JavaScript. Передавать данные безопасной сериализацией, учитывать JavaScript- и HTML-контексты, использовать безопасные DOM-свойства для текста/значения поля. Если inline-строка сохраняется, нужен проверенный контекстный encoder, включая обработку обратной косой черты. CSP применять дополнительным слоем. Проверить аналогичные места поиска, ошибок и форм входа. В браузерных регрессионных тестах использовать комбинации кавычек, обратных косых черт и закрывающих тегов; не должно быть выполнения кода.

Практика: [OWASP Cross Site Scripting Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html).

### 4.3. F-03 — Внедрение HTTP-заголовка через category (CRLF)

| Поле | Значение |
|---|---|
| Класс | HTTP response header injection / CRLF injection |
| Статус | valid |
| Риск / приоритет | Medium / P3 |
| Расположение | `GET /catalog`, параметр `category`, заголовок `Set-Cookie` |
| Модель атакующего | Неавторизованный посетитель; для воздействия на другого пользователя потребуется доставка ссылки или дополнительная цепочка |

**Описание и механизм.** Приложение записывает выбранную категорию в cookie. В значении `category` принимаются URL-кодированные CR и LF. После декодирования они разрывают строку заголовка, и следующий фрагмент воспринимается как самостоятельный HTTP-заголовок ответа.

**Метод обнаружения.** Сравнение заголовков контрольного запроса и запроса с безопасным маркером `X-Practice-Poc`. Проверялось наличие поля в заголовках, а не просто текста в HTML. Подтверждение повторено.

**PoC.** Сначала выполнить контроль:

```bash
curl -sS --max-time 25 -D - -o /dev/null \
  'https://ginandjuice.shop/catalog?category=Gin'
```

Затем через секунду выполнить:

```bash
curl -sS --max-time 25 -D - -o /dev/null \
  'https://ginandjuice.shop/catalog?category=Gin%0D%0AX-Practice-Poc%3A%20GJ-20261106'
```

Payload в наглядной записи (`\r\n` обозначает реальные CR/LF):

```text
Gin\r\nX-Practice-Poc: GJ-20261106
```

**Ожидаемое поведение.** Значения с управляющими символами отклоняются до формирования cookie; отдельный пользовательский заголовок не появляется.

**Фактическое поведение и доказательства.** В исходном ответе маркера нет, в изменённом и повторном есть:

```http
Set-Cookie: category=Gin
X-Practice-Poc: GJ-20261106; Secure; HttpOnly
```

Суффикс `Secure; HttpOnly`, предназначенный для cookie, попал в значение внедрённого заголовка. Ответ имеет статус 200. [Контроль](evidence/header-control.txt), [первое подтверждение](evidence/header.txt), [повтор](evidence/header-repeat.txt).

**Влияние и риск.** Подтверждён контроль над дополнительным полем HTTP-ответа, то есть нарушение его целостности. Более серьёзные цепочки с cookie, перенаправлениями или кэшированием зависят от обработки конкретных заголовков браузером и промежуточными узлами. Они не проверялись; полноценное разделение ответа на два HTTP-сообщения, утечка данных и cache poisoning не заявляются. Medium отражает доказанную инъекцию заголовка при ограниченной проверке конечных последствий. Влияние на доступность не установлено.

**Рекомендации.** Проверять `category` по списку категорий и отклонять CR, LF и другие управляющие символы после декодирования. Для cookie и заголовков использовать штатный API с проверкой значений, не формировать их конкатенацией сырых строк. Проверить все пользовательские значения в `Location`, `Set-Cookie` и служебных заголовках. Добавить интеграционный тест: `%0D%0A` не создаёт нового поля ответа; категория с недопустимыми символами отклоняется.

Практики: [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html); механизм описан в [OWASP HTTP Response Splitting](https://community.owasp.org/attacks/HTTP_Response_Splitting). Ссылка на response splitting объясняет семейство атак, но не означает, что здесь доказано разделение на два ответа.

## 5. Неподтверждённые гипотезы и отрицательные проверки

| Проверка | Источник | Статус | Результат |
|---|---|---|---|
| XSS через одну кавычку без `\` | Ручная проба | Этот payload не подтвердился | Кавычка экранируется; [ответ](evidence/xss.txt) |
| XSS через закрытие script-тега | Ручная проба | Этот payload не подтвердился | Угловые скобки HTML-экранируются; [ответ](evidence/xss-tag.txt) |
| Вариант с присваиванием title в двойных кавычках | Ручная проба | Не использован как доказательство | Двойные кавычки превращаются в HTML-сущности; [ответ](evidence/xss-backslash.txt) |
| Одиночная кавычка в category | Ручная проба | Информационная утечка не подтверждена | HTTP 500 с общим Internal Server Error, без SQL/stack trace; [ответ](evidence/error-handling.txt) |
| Prototype pollution в блоге | Перечень стенда и просмотр клиентских скриптов | Не проверено динамически | В итоговые три находки не включено |

Отрицательный результат отдельного payload не доказывает отсутствие уязвимости. Находки SSRF, IDOR и CSRF из примера задания не переносились в этот отчёт. Отсутствие HttpOnly у служебной cookie балансировщика не оформлялось как самостоятельная уязвимость.

## 6. Приоритеты исправления

| Приоритет | Находка | Причина | Критерий закрытия |
|---|---|---|---|
| P1 | F-01 SQL injection | Управление серверной выборкой без входа, потенциальный риск БД | Параметризация внедрена; условия true/false не интерпретируются как SQL |
| P2 | F-02 XSS | Подтверждён JavaScript в доверенном origin при открытии ссылки | PoC остаётся данными; браузерный тест не фиксирует выполнение |
| P3 | F-03 CRLF | Подтверждена подмена структуры заголовков; дальнейшие цепочки не исследованы | Управляющие символы отклоняются, дополнительного заголовка нет |

Приоритет — порядок работы команды, а не отдельная шкала риска. F-02 и F-03 могут исправляться параллельно.

## 7. Итоговые рекомендации

1. Централизовать параметризованный доступ к БД и применять минимальные права учётной записи приложения.
2. Исключить сборку исполняемого JavaScript из пользовательских строк; применять контекстное кодирование и безопасные DOM-операции.
3. Ввести единую обработку cookie/HTTP-заголовков с запретом управляющих символов и корректной валидацией после декодирования.
4. Добавить регрессионные проверки трёх PoC и ограниченный DAST на staging с явным scope и лимитами нагрузки.
5. Вести карту входных параметров и опасных мест их использования, назначить владельцев исправлений и провести повторную проверку после изменений.
